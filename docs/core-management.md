# Core Management — module detail

Internal task-tracking module. **Not a department** — no department card, not in the switcher, not in `core.departments`/`DEPARTMENTS`. Replaces the old Google Sheets + Apps Script tracker (master sheet + 5 per-department sheets synced every 60s, Apps Script triggers, daily flat email reminders) entirely. That system is fully retired — a one-time historical import brought its 148 real tasks across (see "Historical data import" below), but there is no ongoing sync and never will be.

## Access model

Restricted to exactly two people: Praagya and Amit, both `role='admin'` in `core.users`.

This is a **deliberate identity-based exception** to the platform's normal role-based access model (`core` schema's three-tier admin/dept-admin/member system documented in the root `CLAUDE.md`). Do not "fix" this into a role-based check later — the spec explicitly requires exactly these two people, not "any global admin," and not extensible to department admins or regular members in v1.

Mechanism:
- `core.core_management_admins` — allowlist table, `user_id uuid primary key references core.users(id)`.
- `core.is_core_management_admin()` — `SECURITY DEFINER` SQL function, `select exists(... where user_id = auth.uid())`. Same shape as the existing `core.is_department_admin(dept)` helper.
- Enforced in **RLS on every `core_management.*` table** (`for all using (core.is_core_management_admin())`) and in the **frontend guard** `src/components/RequireCoreManagementAdmin.tsx`, which calls the same function via `supabase.rpc('is_core_management_admin')` — no separate hardcoded list on the frontend, so there's no drift between what the UI shows and what queries actually succeed.
- To add a third admin later: insert their `user_id` into `core.core_management_admins`. No RLS policy or guard code needs to change.

## Schema (`core_management`)

- **`tasks`** — `task_number` (e.g. `T001`) is generated by `core_management.task_number_seq` + a `before insert` trigger (`set_task_number`), never derived from row count — deleting a task never frees its number for reuse. `priority` is `tasklist | active | delayed | other` — see "Data model: priority, delayed, hidden, deleted" below for how this replaced the old `priority` + `is_delayed_manual` pair, as of pass 6 (blocked, not yet migrated). `initial_deadline` defaults to `current_deadline` on insert (`set_initial_deadline_on_insert`) and is then locked forever for non-admins (`lock_initial_deadline` trigger raises on any change; the admin-bypass version is written but also not yet migrated — see "Manual steps required") — both are nullable, since real historical data showed ~49% of tasks (73/148) never had a deadline at all (loose tasklist items); `current_deadline` was originally `not null` but was relaxed after the import revealed this. `is_deleted`/`deleted_at`/`is_hidden` (pass 6, also blocked) back the soft-delete and hide-from-default-views features — see the data model section. `status`/`official_remarks`/`priority`/etc are admin-only-writable — enforced by the `restrict_staff_task_updates` trigger, which raises if a non-admin tries to change anything except `current_deadline`, even within their own row.
- **`task_remarks`** — append-only. No update/delete RLS policy for anyone, including admins, by design (matches the old system's "single overwritten free-text cell" problem being explicitly replaced by a timeline).
- **`today_points`** — `converted_task_id` is set only via the explicit "Convert to Task" button (`convertPointToTask` in `src/lib/coreManagement/db.ts` — two separate calls: insert the task, then update the point. Never a trigger, never automatic).
- **`meetings`** — scaffold only. No AI extraction, no Notion integration this pass.
- **`scratch_sheets`** — best-effort. Plain `title`/`content` textarea per sheet, not a spreadsheet grid — simplified deliberately per spec's own allowance to avoid over-building an ad-hoc tool.
- **`notifications`** — `recipient_user_id`, `task_id` (nullable — null for the digest summary row), `kind` (`urgency_digest` | `task_reminder`), `is_read`. Scoped generically by recipient, not hardcoded to the two admins, so it could extend later without a schema change.
- **`core_management.staff_own_tasks_view`** — the staff-facing surface. Explicit column allowlist (`id, task_number, task_description, department, added_at, current_deadline, responsible_user_id`) — deliberately excludes `status`, `official_remarks`, `priority`. RLS is row-level, not column-level, so a raw `select *` on `tasks` would otherwise leak those columns to a staff session even with correct row scoping; this view is the real enforcement, not just frontend query discipline. As of pass 6 (blocked, see below) the view's own `where` clause also excludes `is_deleted = true` rows outright, so a soft-deleted task disappears from a staff session too, not just from the admin views.

## Staff input surface (separate, minimal)

Route `/my-tasks`, page `src/pages/coreManagement/StaffMyTasks.tsx`. Deliberately outside any `/core-management` path prefix. First `supabase.channel()` usage in this codebase. `src/hooks/useCoreManagementRealtime.ts` subscribes to `postgres_changes` on `core_management.tasks` and `task_remarks`; callers upsert-by-id into local state rather than refetching. Used by Active/All/Delayed Tasks and Task Detail. `NotificationBell.tsx` has its own separate subscription filtered to the signed-in user's notifications.

## Table interaction model — the standard for `TaskTable.tsx`

As of pass 8, this is the one interaction system every column in the task table uses — not a per-column special case, and not something to redesign piecemeal in a future pass. If a future request wants "X to work like Sheets," check here first; the mechanism to hang it off almost certainly already exists.

**Selection vs. editing are two different states**, tracked as `{ taskId, colKey }` coordinates in `TaskTable`'s own state (`selected`, `editing` — never per-cell local state, so exactly one cell in the whole table can be selected or editing at a time, matching a real spreadsheet):
- **Click** a cell → **selects** it (a `ring-2 ring-accent` outline on the plain display value). Does *not* open an editor. This was the core missing piece before pass 8 — every column used to be "always live," which is also what made the reflow/remount bugs from earlier passes possible to have at all.
- **Double-click**, or **Enter** while selected → enters **editing** for that cell, mounting the real control for that column type (textarea/select/date/combobox — see below).
- **Typing a printable character** while a text-capable cell (Task, Remarks) is selected starts editing with that character seeded, replacing the cell's content — the standard spreadsheet "just start typing" behavior. Non-text columns (Select/Date/Combobox) don't do this; Enter or double-click is how those open.
- **Delete/Backspace** while selected clears a text-capable cell (commits an empty value) without needing to enter editing first.
- **Arrow keys** while selected move the selection one cell in that direction — up/down changes row (same column), left/right changes column (same row), skipping the read-only Task # column. Navigation walks the actual currently-rendered row/column order (post sort/filter), not raw DOM order, so it always matches what's on screen.
- **While editing**: Enter commits and moves selection down one row, same column (Shift+Enter instead inserts a newline — Task/Remarks only, the two multi-line columns). Tab commits and moves right one column; Shift+Tab commits and moves left. Escape cancels and reverts to the pre-edit value, no commit.
- Select/Date/Combobox editors commit immediately on choosing a value (their native `onChange`) rather than waiting for Enter — picking a date or an option is itself the "done" signal, same as real Sheets' data-validation cells.

**Per-column editor**, all mounted only while that cell is `editing` (`EditableCell.tsx`, all pure/controlled, no internal open/closed state of their own — that state now belongs entirely to `TaskTable`):
- Task, Remarks → `TextareaEditor` (auto-growing, wraps).
- Department, Status, Priority → `SelectEditor` (native `<select>`).
- Responsible → `ComboboxEditor` (type-to-filter, arrow keys + Enter to pick).
- Added, 1st Deadline, Deadline → `DateEditor` (native `<input type="date">`).
- Task # → never editable (a generated identifier, not a field).

**Multi-row selection is separate from cell selection** — Ctrl/Cmd+click or Shift+click on the serial-number cell toggles/range-selects whole rows (`selectedRowIds`, highlighted `bg-accent/10`) for bulk actions; a plain click there still does its pre-existing job (expand/collapse the remarks timeline). Shift+click extends from the last-clicked row through the clicked one, in whatever order the rows currently render in (post sort/filter).

**Right-click opens a context menu** (`ContextMenu`, styled like a native OS menu — Hide row(s) / Duplicate row (single-row only) / Delete row(s)) at the cursor position, clamped so it never renders off-screen. If the right-clicked row is already part of a multi-row selection, the menu's actions apply to the whole selection (`Delete rows (3)`); otherwise they apply to just that one row, and right-clicking a row outside the current selection replaces the selection with just that row first.

**Hide is per-row and reversible per-row, not a global toggle.** `hiddenIds` is a plain `Set<string>` in `TaskTable`'s own state — never written to the database (see the Data model section's note on why `is_hidden` was dropped from the schema plan). Hiding a row removes it from view instantly, no confirmation. A small "Hidden (N)" control (only shown once N > 0 has ever happened this session — it's always there, just says "(0)" otherwise) opens a panel listing every hidden task by number and description, each with its own "Unhide" button — restoring one specific row, not an all-or-nothing reveal.

**Column headers sort and filter**, both table-wide concepts. Clicking a header's label toggles asc → desc → unsorted (a chevron shows the current direction); clicking the small filter icon opens a checkbox list of every distinct value currently in that column (Select all / Clear, then Apply) — works identically for categorical columns (Responsible, Department, Status, Priority) and date columns (checking specific dates), satisfying "filter to 2 specific Responsible people" and "any date column" with one mechanism rather than two different filter widgets for different column types. In grouped (department-wise) mode, **only the first department group's header is interactive** — sort/filter apply to the whole table regardless of which group you'd click from, so making every repeated header's controls independently clickable would open the same dropdown multiple times at once (a real bug caught during this pass's own verification, fixed by gating a `Header` `interactive` prop). Later groups still show the current sort indicator and an active-filter dot, just not a second live control.

**Bold and italic persist as plain-text markers, not a schema change.** `**bold**` / `*italic*`, applied via Ctrl/Cmd+B / Ctrl/Cmd+I on the current text selection inside an editing Task/Remarks cell (`applyFormat` in `EditableCell.tsx`) or the remarks compose box. `renderRichText` is the read-side parser, shared by the cell's own display state (not just the remarks timeline as it was before pass 8) — so formatting applied in the grid is visible in the grid, not only after expanding remarks. Known, accepted limitation: applying italic to a selection that's already fully `**bold**` (or vice versa) can misdetect "already wrapped" and unwrap incorrectly, since a bold span's edges also technically start/end with a single `*` — true nested bold+italic wasn't asked for and doesn't justify a full markup parser for this.

**Bulk operations are the same code path as single-item ones, not a special case.** `onDeleteTasks(tasks: Task[])` (context menu Delete, whether 1 row or N) and `useUndoableDelete`'s `requestDelete(item | item[])` both accept one item or many uniformly — a bulk delete gets one combined 5s-undo toast and one combined commit call, not N independent ones. This was a deliberate fix, not incidental: N independent timers each racing an "is something already pending" check was the actual mechanism behind "deleting multiple tasks produces Failed to delete task" (see "UX rework, pass 8" below for the other half of that bug).

## UX rework, pass 2 (post-launch feedback)

After the first build, direct usage feedback was: this should feel like an upgraded Google Sheet — fast, dense, editable inline — not a modal-heavy CRUD app. This pass reworked the module around that principle. Built on the `core-management` branch, mid-pass the Supabase MCP connection dropped with no local fallback (no CLI, no `psql`, no service-role key) — everything below shipped except the three items explicitly marked **blocked**, which are fully coded and ready, just not deployed/migrated yet.

**Layout** — sidebar is now collapsible (`src/hooks/useSidebarCollapse.ts`, Ctrl/Cmd+B, `localStorage`-persisted). Decorative subtitle lines under page titles were removed everywhere. Spacing tightened within `docs/design-system.md`'s approved 8px-multiple scale (4/8/12/16/24/32/48 — not just "smaller").

**Table header styling** — sky-blue-tinted header row (`bg-accent/8`, `border-accent/25`) instead of the old neutral `surface-2` header, closer to the old sheet's look. This is the existing single `--accent` token at low opacity, not a new color — stays within the design system's "no more than one accent color" rule.

**Inline editing** — `src/components/coreManagement/TaskTable.tsx` is now the shared table for Active/All/Delayed Tasks, replacing per-page table markup + the old `NewTaskModal`-as-only-add-path + the separate task-detail page.
- Cells are always-live inputs/selects (`src/components/coreManagement/EditableCell.tsx`), not a click-to-reveal-editor toggle — clicking a cell focuses it directly, exactly like a spreadsheet. Text commits on blur/Enter; select/date/checkbox commit immediately on change.
- An inline "add row" (`AddRow` inside `TaskTable.tsx`) replaces the modal for normal task creation — type description, pick responsible/department/deadline, press Enter or click the `+`.
- Remarks are an expandable sub-row (`RemarksSubRow`, toggled by a message icon per row) — a genuinely different interaction (a log, not a field), kept separate per the spec's own carve-out. `NewTaskModal.tsx` still exists but only for the Today's Points "Convert to Task" flow, which pre-fills fields and is a deliberately distinct action.
- All edits are optimistic (`ActiveTasks`/`AllTasks`/`DelayedTasks`'s `handleUpdateTask`): local state updates immediately, the real request fires in the background, and only a failure triggers a full reload-and-revert.

**Column visibility** — every column (including `task_number`) is toggleable via the "Columns" button (`src/components/coreManagement/ColumnsMenu.tsx`), backed by `src/hooks/useColumnVisibility.ts`. *(Originally shipped as two independent screen/print visibility sets — consolidated to one shared set per view in pass 3 below, see that section for why.)*

**Print/PDF rebuild** — browser Print and PDF now render from the same source data and column set, and look consistent with each other:
- `src/components/coreManagement/PrintTable.tsx` — a plain read-only table (no form controls) shown only under `@media print` via a new `.cm-print-only` class (the interactive `TaskTable` is `.cm-no-print`, hidden only when printing) — see `src/index.css`'s `.cm-print-*` rules for the thin-border, sky-blue-header, tight-row styling matching the old sheet's actual printout.
- `exportToPDF()` (`src/lib/coreManagement/exportUtils.ts`) uses matching colors/borders via `jspdf-autotable`.
- Orientation is chosen per view (`ExportButtons`'s `orientation` prop) — landscape for the wide task tables, portrait for Today's Points/Meetings. `printCurrentView(orientation)` rewrites a `<style id="cm-print-page-style">` tag's `@page` rule just before calling `window.print()`, so the browser's print dialog opens with the right orientation pre-set.

**Admin-only `initial_deadline` unlock — blocked, migration ready.** The `lock_initial_deadline` trigger currently rejects any change to a non-null `initial_deadline` for everyone, including admins. The fix (allow `core.is_core_management_admin()` to bypass it; staff stay exactly as restricted as before) is a one-statement `create or replace function` — not run yet, blocked on the Supabase MCP outage:
```sql
create or replace function core_management.lock_initial_deadline()
returns trigger language plpgsql
set search_path = 'core_management', 'core', 'pg_temp'
as $$
begin
  if core.is_core_management_admin() then
    return new;
  end if;
  if old.initial_deadline is not null and new.initial_deadline is distinct from old.initial_deadline then
    raise exception 'initial_deadline is locked once set';
  end if;
  return new;
end;
$$;
```
Until this runs, `TaskTable` deliberately renders `initial_deadline` as read-only text rather than an editable field that would just fail on save (see the comment at that column's `case` in `TaskTable.tsx`).

**Loading-flicker reduction** — every list view now only shows a "Loading…" state on genuine first-load-with-no-data (`loading && tasks.length === 0`), not on every subsequent action; realtime already merged incrementally rather than refetching. **Platform-wide note, not fixed here**: this same "blank the whole page on every navigation" pattern likely exists in other modules (Purchase, Admin) built before this convention existed — worth raising in the platform's main chat as a general pattern to adopt, not something this pass touched outside Core Management.

**Scratch Sheet — real grid, no schema change.** `src/lib/coreManagement/grid.ts` defines a `{rows, cols, cells}` model serialized as JSON into the *existing* `scratch_sheets.content` text column — add/remove rows and columns, per-cell editing, autosave (500ms debounce) on every change. No formulas, no cell references — a plain grid, not a spreadsheet engine, per the spec's own scope note. Old plain-text sheets from the earlier build are preserved (dropped into cell A1) rather than discarded if `content` doesn't parse as the new JSON shape.

**Manual reminder triggers.** `supabase/functions/core-management-digest/index.ts` now serves two callers: the daily cron job (`Authorization: Bearer <service role key>`, unchanged behavior) and, new, a signed-in admin calling it directly (`Authorization: Bearer <their session JWT>`, POST body `{scope: 'all'|'department'|'user', departmentKey?, userId?}`) — verified against `core.core_management_admins` before doing anything, since this is now reachable from the browser rather than only from the trusted cron path. A manual send bypasses the quiet-window/interval throttling (an explicit click should always send) but still only for tasks in the overdue/approaching tiers. Frontend: `src/components/coreManagement/ReminderTrigger.tsx` (bell icon in the shell header) → "Send to all" / "By department" / "By individual". **Blocked**: the *updated* function needs redeploying (it was previously deployed as cron-only, without the manual-trigger branch) — the UI and function code are both finished, this is purely a deploy step once Supabase access is back.

**AI task extraction — v1 only, general-purpose.** New edge function `supabase/functions/core-management-ai-extract/index.ts`: accepts pasted text and/or a WhatsApp screenshot image, calls Claude (with the department list and active-user roster in the prompt for best-effort matching) to extract candidate tasks as JSON, and returns them — it **never saves anything itself**. Frontend `src/pages/coreManagement/AIExtractModal.tsx` ("Add via AI" button next to Export/Columns on Active/All Tasks) always shows the extracted task(s) as an editable confirmation form (description, department, responsible, deadline all fuzzy-matched but changeable) before a normal `createTask()` call runs — extraction never auto-saves. **This is explicitly v1**: general-purpose extraction, not tuned to any one person's shorthand or writing style. Personalizing it (learning a specific person's abbreviations, phrasing patterns, etc.) is an **explicit v2**, to be designed once real example messages are available — don't build that without being asked, and don't assume v1's generic prompt is "not good enough" without checking with Praagya/Amit first. **Blocked**: this is a brand-new function, never deployed — also needs `ANTHROPIC_API_KEY` (same secret the digest function already uses) to be readable by this function too (Supabase edge function secrets are project-wide, so no extra setup needed there, just the deploy).

## UX rework, pass 3 (consolidated punch list)

A follow-up round combining more direct usage feedback with specific bugs found while using the app. Same Supabase MCP outage as pass 2 — still no CLI/`psql`/service-role fallback — so the same three items plus two new ones are blocked (all fully coded, see the updated "Manual steps required" list below). **Verification note**: live-testing this pass required real credentials for a Core Management admin. `test@basant.info` (given for testing) turned out to be a Purchase-only account, not on the `core.core_management_admins` allowlist — confirmed directly by driving a headless browser through login: it authenticates fine and lands on `/purchase`, but navigating to `/core-management` silently redirects away (`RequireCoreManagementAdmin` doing exactly what it's designed to do). That did let me verify the login flow, RLS grants, and the `/my-tasks` staff surface end-to-end with zero console/network errors — but the admin-only views below (the bulk of this pass) are verified by code/logic review only, not click-tested live, until a real Praagya/Amit session is available.

**Column visibility, consolidated to one set.** Pass 2 shipped independent screen/print visibility per view; this pass's spec asked for print to "respect whatever the column-visibility toggle is currently set to," which only holds cleanly with a single shared toggle. `DEFAULT_VISIBLE_COLUMNS` (`src/lib/coreManagement/columns.ts`) is now one list — `task_description, responsible, initial_deadline, current_deadline, official_remarks` (serial # is always shown, never a toggle) — governing the on-screen table, Print, PDF, and Excel identically. Toggling a column on shows it everywhere at once.

**Borders.** Every cell in `TaskTable` now has a full `border-border` outline (not just row bottoms) for a real grid look; the header uses `border-accent/20` dividers. Print/PDF/Excel all use the same 1px `#9fb4e0` (medium, not heavy) border weight for visual consistency across every output.

**Department group heading.** Bumped from `text-xs font-semibold text-text-secondary` to `text-base font-bold text-text` — clearly more prominent than the `text-xs` column headers below it.

**Compact/wide columns.** `TaskColumnDef.width` (`'wide' | 'compact'`) — Task/Remarks are `wide` (`min-w-[220px]`), Department/Responsible/dates/etc are `compact` (`w-24`). **Deferred**: true drag-to-resize columns were not built this pass — fixed compact widths were used instead, per the spec's own explicit fallback allowance ("if full drag-resize is out of scope this pass, use sensible fixed compact widths instead"). Revisit if the fixed widths turn out to be wrong for real content.

**Short dates everywhere.** `formatShortDate()` (`src/lib/coreManagement/taskHelpers.ts`) — "26 Aug" / "13 Sept" (note: `Sept`, not `Sep`, matching the spec's literal example — every other month keeps its standard 3-letter form). Parsed from the `YYYY-MM-DD` string directly rather than via `new Date()`, to avoid a timezone-shift bug where `new Date('2026-08-26')` (UTC midnight) can render as the 25th in a negative-offset local timezone. Applied in `TaskTable`, `PrintTable`, Excel export, and Today's Points/Meetings. `EditableDate` (`src/components/coreManagement/EditableCell.tsx`) shows this short format at rest — a native `<input type="date">` always renders in the browser/OS's own locale format with no way to override it, so the resting state is a plain formatted button that swaps in the real date input (auto-focused, opens the picker) only while editing, then swaps back.

**Toggle labels.** "Grouped" → "Department wise", "Flat" → "All Tasks" (`AllTasks.tsx`).

**Department list scoped to exactly 8.** `useDepartments()` (`src/hooks/useDepartments.ts`) now filters to `sales, purchase, production, operations, wip_praagya, wip_amit, wip_others, orange_tree` and overrides the WIP labels to the exact requested casing (`WIP PRAAGYA`/`WIP AMIT`/`WIP OTHERS`) — **client-side only, `core.departments` itself was not touched**. That table is shared platform infrastructure: `purchase`/`production`/`sales`/`hr`/`yaamya`/`admin` power the real department switcher for *every* module, not just Core Management, and deleting or renaming rows other modules depend on would be a genuinely high-blast-radius change outside this module's remit (and outside what was asked). The generic `wip` key (confirmed unused by any real imported task) is safe to actually delete once DB access returns, as a cleanup, but isn't required for correctness since the frontend filter already excludes it everywhere Core Management reads departments.

**Admin-only `initial_deadline` unlock** — still blocked, migration unchanged from pass 2 (see below).

**Delete task.** New — a trash icon per row in `TaskTable` (visible on hover), `window.confirm()` before calling the new `deleteTask()` (`src/lib/coreManagement/db.ts`), optimistic removal with rollback on failure. Available everywhere `TaskTable` is used (Active/All/Delayed).

**Today's Points bug fix.** The reported symptom ("No points logged" persists, adding does nothing) traced to `handleAdd()` having **no error handling at all** — any failure (RLS, network, anything) became an unhandled promise rejection inside the click handler, which silently aborts the function: `setPoints`/`setShowAdd(false)` never run, and nothing tells the user anything went wrong. Fixed with a real `try/catch` + visible error message (dismissible, matches the pattern now used in `ActiveTasks`/`AllTasks`/`DelayedTasks`). Also applied the same fix to `load()`. **Root cause not 100% confirmed live** (blocked on real admin credentials, see the verification note above) — but the silent-failure bug was real and is fixed regardless of whether it was the exact thing that failed for you; if it recurs, the error will now say why.

**Scratch Sheet delete + rename.** `deleteScratchSheet()` (new, `db.ts`) wired to a trash icon per sheet in the sidebar list (confirm prompt). Rename via double-click on a sheet's name in that same list (inline text input, commits on blur/Enter) — the open sheet's own title field already worked as a rename mechanism in pass 2, but wasn't obviously discoverable in the sidebar list itself, which is what this adds.

**Excel export rebuilt with real styling.** The `xlsx` package (SheetJS Community Edition, already used elsewhere in the app for *importing* HC-extraction spreadsheets) has no cell-styling support at all in its free tier — the old Excel export was a raw `json_to_sheet` dump. Added `exceljs` (a genuinely styling-capable library, MIT-licensed) for Core Management's exports specifically; `xlsx` stays exactly where it already was for HC-extraction import, untouched. New `exportToExcel()` (`src/lib/coreManagement/exportUtils.ts`) produces: bold header row with the same sky-blue fill as Print/PDF, `1px` borders on every cell, per-column widths (`excelWidth()` in `columns.ts`, matching the wide/compact hints above), word-wrap on body cells, and a frozen header row. `npm audit` flags a moderate transitive `uuid` advisory via `exceljs` (buffer-bounds issue in a code path this app's usage — generating our own exports from trusted internal data, never parsing untrusted input — doesn't hit) and the pre-existing high-severity `xlsx` advisory (unrelated, already present before this pass, no fix available upstream).

**Manual reminder triggers & AI extraction** — unchanged from pass 2, still both fully coded and still both blocked purely on deployment (see below); UI is intact.

## UX rework, pass 4 (table-rendering + input-behavior punch list)

A 9-item punch list from direct usage: text truncation, a redundant remarks affordance, delete-button placement, remark-input Enter behavior, print/PDF/Excel column-width consistency, date-field stability, the still-broken `initial_deadline` admin unlock, print orientation, and a searchable Responsible field. ## UX rework, pass 5 (reproducible-bug punch list)

Four precise, reproducible bugs found while actually using pass 4's rebuild: bold formatting missing from remark text, the delete button still visually mispositioned, Added/1st Deadline not editable, and a cell-click dead zone. Same Supabase outage as passes 2–4 (no MCP/CLI/`psql`), but this pass didn't touch anything DB-side — everything below is a pure frontend fix and was reproduced and re-verified live via the same kind of temporary mock-data harness used in pass 4 (added, driven with Playwright, then removed — see "Verification method" below).

**Bold formatting — new capability, not a pre-existing broken toggle.** There was no rich-text toolbar or Ctrl+B handling anywhere in the codebase before this pass (confirmed by grep) — remarks were, and text fields still are, plain `<textarea>` elements, which never support browser-native bold. Scoped specifically to the **remark compose-and-display flow** (`RemarksSubRow` in `TaskTable.tsx`), not `task_description`/`official_remarks` — those two remain plain always-live editable cells with no separate "posted/rendered" view to show real bold in (see pass 2's "always-live cell" architecture), so there's nowhere to display them as actually bold; extending bold there would just mean showing literal `**asterisks**` permanently in the cell, which reads as a bug of its own. This is a judgment call, flagged the same way pass 4's remarks-button consolidation was.

Implementation: `applyBold()` toggles a `**bold**` markdown wrapper around the current `<textarea>` selection (wraps if unbolded, unwraps if the selection exactly matches an existing `**…**` span, inserts an empty `****` pair with the cursor centered if nothing's selected) — bound to `Ctrl/Cmd+B` and a new toolbar "B" button (`lucide-react`'s `Bold` icon) next to Post. The toolbar button uses `onMouseDown={e => e.preventDefault()}` to stop the textarea from blurring (and its selection collapsing) before the click fires — the standard trick every toolbar-style text editor needs. No schema change: `remark_text` stays plain text, with the markers stored literally. `renderRemarkText()` is the read-side counterpart — splits on `**…**` and renders those spans as real `<strong>` when a posted remark is displayed in the timeline, so bold survives reload as actual bold, not literal asterisks. Verified in isolation with a plain Node script (not part of the app) confirming both the wrap/unwrap/insert-empty toggle logic and the split-and-render parser against several inputs (mid-string bold, string-start bold, multiple bold spans, unmatched `**`, empty string) before wiring into the UI, then confirmed live: selecting a word in the compose box and pressing Ctrl+B visibly wraps it in `**…**` with the new markers left selected (so a second Ctrl+B correctly unwraps).

**Delete button — actually swapped to the leading edge, not just restyled.** Pass 4 had already moved delete out of the far-right end, but only as far as the *second* column (right after serial #), which is what still read as "next to the row number, awkwardly positioned" in the screenshot. Now genuinely first: delete's `<td>` renders before the serial-number `<td>` in `Row`, `AddRow` (its `+` button swapped to the same leading slot), and `Colgroup` (icon-column width first, serial-column width second) — consistent left edge across every row, confirmed by inspecting the actual rendered cell order, not just the source order.

**Added / 1st Deadline now editable, same as Deadline.** Both switched from a plain read-only `<span>` to `EditableDate` (`case 'added_at'` and `case 'initial_deadline'` in `TaskTable.tsx`'s `renderCell`) — clickable, opens the native date picker, commits on change, exactly like `current_deadline` already did. `initial_deadline` staying editable in the UI despite the still-unrun admin-unlock migration (see pass 4 and "still blocked" below) is deliberate, not an oversight: the currently-live `lock_initial_deadline` trigger only rejects changing a value that's already non-null — a task whose `initial_deadline` is still `null` can genuinely be set today, and an edit that does get rejected surfaces through the existing update-error banner (`handleUpdateTask`'s try/catch, already in place since the original build) rather than failing silently. Read-only-until-migration would have hidden that first-time-set case for no reason.

**Cell-click dead zone — root cause, not a per-column patch.** The reported bug (a red/yellow box comparison screenshot: a small clickable sub-region vs. the full visible cell) traced to every interactive control (button, select, input) only being as tall as its own content, while the surrounding `<td>` can be taller whenever a *different* cell in the same row is taller — most commonly a long-wrapped `task_description` forcing the row height while a `Responsible`/date/select cell next to it stays short, leaving a visible-but-unclickable strip below the control. This also affected the two textarea columns themselves relative to each other (`task_description` vs `official_remarks`), not just the non-textarea fields. Rather than fighting CSS `height: 100%` against `EditableTextarea`'s own JS-driven `scrollHeight` sizing (fragile, and wouldn't generalize to every control type), the fix is a single delegated click handler (`focusCell` in `TaskTable.tsx`) on every data-column `<td>`: if the click landed on the cell itself (not already on its input/textarea/select/button), it finds that one descendant and focuses it — or, for click-to-edit buttons like `EditableDate`/`EditableCombobox`, calls `.click()` on it so the same code path that normally opens the picker/dropdown runs. Verified live: with a row made deliberately tall by a long `task_description`, clicking a pixel a few rows below the visible "Amit Jain" button in the (short) Responsible cell correctly opened the searchable combobox.

**Verification method this pass.** Same constraint as pass 4 — no working Core Management admin credentials, `test@basant.info` is Purchase-scoped only. A temporary unauthenticated route (`/dev-test-tasktable`, mock data crafted specifically to reproduce the dead-zone shape — one row with a long `task_description` next to short `Responsible`/date/`official_remarks` cells) was added, driven with Playwright to reproduce each of the four bugs as described (not just re-check that the code compiles), screenshotted, then **removed** before finishing. The one console error seen while testing (`400` from a `task_remarks` query, `PAGEERROR: Object`) is the harness's fake, non-UUID mock task ID hitting the real Supabase REST endpoint — an inherent limitation of testing without a real task row, unrelated to this pass's changes, and the same category of harmless noise documented in pass 4. Real end-to-end confirmation of the DB-backed pieces (posting an actual bold remark and reloading, editing `initial_deadline` on a real task, deleting a real task) still needs a real Praagya/Amit session.

## UX rework, pass 6 (delete safety, layout/columns, sorting, priority, reminder placement)

A 12-item punch list: soft-delete + undo, three column/layout fixes, two bugs (a page-load layout glitch and a print/PDF header-data audit), and three new features (hide-without-deleting, click-to-sort, and the Priority dropdown that drove the data-model change documented above). Same Supabase outage as passes 2–5 — re-confirmed at the start of this pass (no MCP, no CLI, no `psql`, only the anon key in `.env`) rather than assumed from prior notes. Everything schema-dependent is written and ready but **not migrated** — see "Manual steps required". Everything frontend-only shipped and was verified live via the same kind of temporary mock-data harness used in passes 4–5 (added, driven with Playwright, then removed).

**Soft delete + 5s undo.** Delete everywhere in the admin UI now calls `softDeleteTask()` instead of a hard `.delete()` — see the Data model section above for the full is_deleted/is_hidden reasoning. `src/hooks/useUndoableDelete.ts` is the shared mechanic behind the 5s grace window: the row leaves local state immediately (so the UI feels instant), but the real soft-delete call is deferred behind a `setTimeout`; clicking "Undo" on the toast (`DeleteUndoToast.tsx`, bottom-right) within that window cancels the timer and restores the row, and never calls the API at all. Deleting a second task while one is still pending commits the first immediately rather than silently dropping it. **The old `window.confirm()` before delete was removed** — the undo window supersedes it as the accidental-delete safeguard, and a blocking confirm on top of a 5s undo would just be redundant friction. **Deleted Tasks view.** New `src/pages/coreManagement/DeletedTasks.tsx`, route `/core-management/deleted`, added to the shell nav (now 7 items). **Renumber affordance (item 3).** Serial numbers were already purely derived — `index + 1` over whatever order the array is currently in, recomputed on every render — never a stored value, so there was structurally nothing that could go stale or need fixing. Added the requested button anyway (small icon in the `#` column header, `TaskTable.tsx`) rather than skip it as unnecessary: clicking it triggers a brief highlight pulse across the `#` column as an honest confirmation that numbering is live and correct, instead of quietly doing nothing or fabricating a persisted renumber step that isn't needed. **Layout glitch on page load (item 7) — root-caused to font-swap reflow, not a React re-render.** `@fontsource/inter`'s CSS registers `font-display: swap` on every face; the browser was painting with the fallback font (`system-ui`/Segoe UI/Roboto, per `--font-sans`) first and swapping to Inter once its woff2 finished downloading, and the fallback's glyph metrics differ from Inter's enough that wrapped text — and therefore container sizes — visibly changed on the swap. This was verified, not assumed: a Playwright script hashed every visible element's bounding box at several points after page load under an artificially delayed (2.5s) font response; with the original `swap` behavior the hash changed the moment the font arrived (reproducing the bug on demand), and with the fix below the hash stayed identical at every checkpoint. Side benefit: removed ~30 unused font-subset files from the build.

## Data model: priority, delayed, hidden, deleted

Pass 6 asked for a Priority dropdown (Tasklist/Active Task/Delayed/Other) and explicitly asked for the relationship between that dropdown, the existing `priority` column, and the existing `is_delayed_manual` flag to be resolved into one clean model, not left as two overlapping concepts. Decision made:

**`is_delayed_manual` is retired. `priority` becomes the single source of truth, extended to `tasklist | active | delayed | other`.** Before this pass, a task had a `priority` tier (`active | tasklist | delayed`) *and* an independent `is_delayed_manual` boolean — meaning a task could in principle be `priority='active'` and `is_delayed_manual=true` at the same time, which never had a clear meaning in the UI (the Delayed view showed it under "manually flagged" regardless of its priority tier, so priority was effectively being ignored for delayed tasks anyway). Folding `is_delayed_manual` into `priority`'s existing `delayed` value removes that overlap entirely: a task now has exactly one priority, `delayed` included, and it drives exactly one thing — which view(s) it surfaces in. `other` was added as a genuine fourth tier (tasks that are real work but don't fit Active/Tasklist/Delayed), not a fallback/error value.

**View membership, as implemented in `ActiveTasks.tsx`/`AllTasks.tsx`/`DelayedTasks.tsx`:**
- **Active Tasks** — `priority = 'active'` only.
- **All Tasks** — no priority filter at all; every task regardless of priority appears here (this didn't need to change — `AllTasks.tsx` already fetched unfiltered).
- **Delayed** — two independent sections, unchanged in structure from before: **auto-overdue** (`current_deadline < today AND status != 'done'`, computed live from any task regardless of priority — a `priority='active'` task that's simply late still shows up here) union **manually flagged**, which used to read `is_delayed_manual` and now reads `priority === 'delayed'`. A task can appear in both sections at once if it's both overdue and manually marked delayed; that was already possible before and is unchanged.

This means `priority='delayed'` and being auto-overdue are two genuinely different, independently-true things — "Delayed view" is not itself a priority tier, it's a view that two different signals both feed into. That distinction is why `delayed` stays a `priority` value (an admin's deliberate call that this task is delayed) rather than something the Delayed view derives on its own the way auto-overdue is derived.

**Migration** (writes to `core_management.tasks`, blocked — see "Manual steps required"):
```sql
alter table core_management.tasks
  add column is_deleted boolean not null default false,
  add column deleted_at timestamptz;

-- Fold the old boolean into the new single-select model before dropping it —
-- anything flagged is_delayed_manual becomes priority='delayed', overriding
-- whatever priority tier it had (being manually flagged delayed was always
-- the more urgent, more deliberate signal of the two).
update core_management.tasks set priority = 'delayed' where is_delayed_manual = true;

alter table core_management.tasks drop constraint if exists tasks_priority_check;
alter table core_management.tasks add constraint tasks_priority_check
  check (priority in ('tasklist', 'active', 'delayed', 'other'));

alter table core_management.tasks drop column is_delayed_manual;

-- Staff must never see a soft-deleted task at all, not just have it hidden
-- by the frontend — same column-allowlist-via-view enforcement pattern
-- status/official_remarks/priority already use.
create or replace view core_management.staff_own_tasks_view as
  select id, task_number, task_description, department, added_at, current_deadline, responsible_user_id
  from core_management.tasks
  where responsible_user_id = auth.uid() and is_deleted = false;
```
(No `is_hidden` column — see below. Pass 6 originally added one; pass 7 replaced it with pure client-side state before this migration ever ran, so it was simplified away rather than ever actually existing in the schema.)

**Soft delete vs. "hide" — not two tiers of one state; only one of them is a real database concept.**
- `is_deleted` + `deleted_at` — set by the normal delete action everywhere (`softDeleteTask()` in `src/lib/coreManagement/db.ts`). A deleted task disappears from every admin view (`fetchTasks()` filters client-side, see "UX rework, pass 6" fix-up note below) and from the staff surface (the view's own `where` clause, above) — but is never actually removed from the table. It moves to the Deleted Tasks view (`DeletedTasks.tsx`), where it can be `restoreTask()`'d back or `purgeTask()`'d — a real hard `delete`, the only place in the app that still issues one, gated by its own `window.confirm()` since that step has no undo at all.
- **"Hide" is deliberately not a database concept at all** — see "UX rework, pass 7" below for why the original `is_hidden` column design was replaced with plain component state before it ever shipped to the database.

## UX rework, pass 7 (interaction feel, visual polish, print/reminder flow)

The app worked functionally after pass 6 but felt slow and under-styled — no hover/active feedback on buttons, a visible reflow on every edit, an orange highlight on date cells nobody had asked for, and a live "Failed to save change" error. This pass fixed the actual root causes rather than masking them, plus delivered three interaction-model changes (spreadsheet-style Enter, a much lighter hide, and Google-Sheets-style print options) under the explicit "Sheet-like speed and directness" direction, keeping `docs/design-system.md`'s visual language (not sheet-like appearance).

**Root cause of "the whole table reflows on every edit" — not a refetch, a remount.** `TaskTable.tsx`'s `Colgroup`, `Header`, `Row`, `AddRow`, and the table wrapper were all declared as functions *inside* `TaskTable`'s own render body. A component declared inside another component's render gets a brand-new function identity every single render; React treats that as an entirely different component type on every re-render and unmounts + remounts the whole subtree rather than reconciling it — destroying and recreating every row's real DOM nodes after every edit, even though the optimistic local-state update itself was already instant. This is also what was silently wiping `AddRow`'s in-progress "New task" input on any unrelated update elsewhere in the table (a second, quieter symptom of the same bug — the add-row's own `useState` was being torn down and recreated along with the remount). **Fix**: `Colgroup`/`Header`/`Row`/`AddRow`/`TaskRowsTable` are now module-level components taking explicit props instead of closing over `TaskTable`'s scope — a stable identity across renders, so React only touches the DOM nodes that actually changed. Verified live (not just assumed from the code): typed draft text into the add-row, triggered a completely unrelated edit on a different department's row, and confirmed the draft text was still there afterward — it would previously have been silently cleared.

**"Failed to save change" — root-caused, not just noted.** Traced to the hide button pass 6 shipped: it called `onUpdateTask(id, { is_hidden: !task.is_hidden })`, and `is_hidden` doesn't exist on the live table (that migration never ran — see "Manual steps required"), so every hide click failed with exactly this error. Fixed as a side effect of simplifying hide itself (below) — hide no longer writes to the database at all, so this failure mode is gone, not just handled more gracefully.

**Hide simplified to pure, disposable client state (item 5) — no longer a database concept.** Pass 6's `is_hidden` column/checkbox/"Show hidden" review flow is gone entirely, replaced with a `Set<string>` of hidden task ids living in `TaskTable`'s own component state — never written to the database, never round-tripped through `onUpdateTask`. Clicking the hide icon removes a row from view instantly (no confirm, no separate screen); a small "N hidden from this view — show" text link (not a checkbox, not a management page) restores all of them at once. This resets on reload by design, matching a spreadsheet's "hide row" rather than a persisted moderation feature — and it happens to remove one of the pass-6 migration's dependencies entirely, since `is_hidden` was dropped from the schema plan before that migration ever ran (see the Data model section above).

**Removed the date-cell warning border (item: visual polish).** `current_deadline` cells for auto-overdue tasks had a 3px `border-warning` left-edge (added in an earlier pass, technically following `docs/design-system.md`'s flagged-row pattern) — removed per explicit instruction that no color-coding on dates should ship until a specific rule is designed. Cells now use the same neutral border as every other cell; `isAutoOverdue`/the overdue computation itself is untouched, only the visual treatment on the date cell is gone.

## UX rework, pass 8 (Sheets interaction model rebuild)

The last several passes had each patched one symptom at a time — sorting added, then keyboard nav requested separately, then rich text, then hide/show reworked twice — because the underlying table was still built around "every cell is always a live input," which structurally can't support click-to-select/arrow-nav/right-click without fighting itself. This pass replaced that foundation once (see "Table interaction model" above for the resulting standard) instead of adding another patch, per explicit instruction. It also fixed two P0 bugs found by direct diagnosis, not guessing, before any of the rework began.

**"Adding a task is broken" — root cause found and fixed.** `AddRow`'s `department`/`responsible` fields were seeded from `useState(departments[0]?.key ?? '')` / `useState(userOptions[0]?.value ?? '')` — a **once**, at-mount-time default. `departments`/`userOptions` are always empty arrays on a page's very first render (a real network fetch hasn't resolved yet), so both fields locked in at `''` and never got a chance to correct themselves once the real data arrived — and `submit()`'s own guard (`if (!responsible) return`) then silently no-op'd every click/Enter, with no error, no feedback, nothing. This is very likely a regression from pass 7's own reflow fix: before that pass, `AddRow` was (unintentionally) remounted on almost every parent re-render, which incidentally "healed" this exact bug by re-running the `useState` initializer against fresher props each time — fixing the remount bug removed that accidental self-correction. **Fix**: two small `useEffect`s backfill `department`/`responsible` from the real options once they load, but only if the field is still at its untouched empty default (so it never clobbers something the user already picked). Verified live under the exact failure condition — typed a task description before the (simulated) 400ms async department/user fetch resolved, waited for it to resolve, pressed Enter — and confirmed the task was created with real `department`/`responsible` values, not empty strings.

**"Bulk delete produces Failed to delete task" — traced to the still-unrun pass-6 migration, plus a real design gap.** Confirmed directly against the live database (`curl` against the REST endpoint) that `is_deleted`/`deleted_at` still don't exist — a write including them returns `PGRST204` ("could not find the column"), so *every* soft-delete write, single or bulk, was unconditionally failing; bulk delete just made this more likely to be noticed since it wasn't built as a real single-request operation before. Two fixes: (1) `softDeleteTasks(ids)`/`purgeTasks(ids)` in `db.ts` now operate on an array via `.in('id', ids)` — one request for N deletes, not N requests — and `softDeleteTasks` catches `PGRST204`/`42703` specifically and falls back to a real hard delete (`purgeTasks`) so the action **actually succeeds now** rather than staying broken until the migration runs; once it does run, the primary soft-delete write starts succeeding and the fallback simply stops triggering, no further code change needed. (2) `useUndoableDelete` now takes `T | T[]` uniformly — a bulk delete is one `requestDelete(array)` call with one combined 5s-undo toast and one combined commit, not N single-item calls each racing the hook's own "something already pending" logic. Verified live: multi-selected 3 rows (Ctrl+click), right-clicked, "Delete rows (3)" — all 3 removed in one call, a 4th untouched row unaffected.

**Reminder dialog (item 6) — could not be matched to a reference.** The prompt referenced an attached sketch/mockup, but no image actually came through in what this session received — there was nothing to compare against or build to. The existing centered-modal reminder dialog (built in pass 7) was left as-is rather than guessed at blind. If the mockup is re-sent, this is a contained, quick follow-up — `src/components/coreManagement/ReminderTrigger.tsx` is the only file involved.

**Everything in this pass was verified by actually driving the running app** (Playwright against a temporary mock-data harness, removed before finishing), not by reading the code and assuming it worked — per the explicit instruction given this module's history of fixes that looked right but weren't clicked. Confirmed live, in order: single-click selects without opening an editor; arrow keys move selection correctly (including skipping the read-only Task # column); double-click opens the real editor; Ctrl+B and Ctrl+I wrap the current selection in `**`/`*`; Enter commits and moves selection down, with the row's new value visibly saved; Escape cancels and leaves the original value in place, uncommitted; Tab/Shift+Tab move column-to-column; right-click opens the context menu; hiding one row removes only that row (a second row stays visible) and the Hidden panel lists and individually unhides it; sorting a column both directions actually reorders rows within their department group without reordering the groups themselves (a real bug caught mid-verification — see "Table interaction model" above — and fixed before calling this done); filtering Responsible to 2 of 4 people shows exactly the right 2 people's tasks; creating a task under the exact async-load race condition succeeds with real field values; duplicating a row creates a copy; and bulk-deleting 3 selected rows removes exactly those 3 and nothing else.

## Reminders

Edge function `supabase/functions/core-management-digest/index.ts`, triggered daily by a `pg_cron` job (`core-management-digest-daily`, `30 2 * * *` UTC = 8:00am IST) via `pg_net`'s `net.http_post`, authenticated with a service-role key stored in Supabase Vault under the secret name `core_management_service_role_key` (never embedded in migration SQL or passed through chat).

Urgency tiers — tunable constants at the top of the edge function, deliberately not a flat daily reminder (the old system's confirmed pain point):
```ts
const QUIET_WINDOW_DAYS = 3          // no reminders in the first N days after added_at
const APPROACHING_DAYS = 5           // start reminding once within N days of current_deadline
const APPROACHING_INTERVAL_DAYS = 2  // remind every N days while approaching
const OVERDUE_INTERVAL_DAYS = 1      // remind every N days once overdue
```
Skips `status='done'` tasks. "Last reminded" is derived by querying `notifications` for that task+recipient, not a separate column.

One AI element: a single summarization-only line at the top of each run's notification batch, generated by calling the Claude API (`ANTHROPIC_API_KEY` — Supabase edge function secret) with the due-task list. Falls back to a rule-based line (`"N tasks overdue, M approaching deadline."`) if the key is absent or the call fails. The AI never decides scheduling, status, or task content — only that one line.

**Resend email digest is an explicit optional stretch, not built this pass.** A seam is left in the edge function (checks for `RESEND_API_KEY`, no-op if absent) so adding it later doesn't require restructuring. **No WhatsApp** — out of scope, no integration point built.

## Historical data import

A one-time import of 148 real tasks from the old system's "Task Management" sheet (`Core Management (7).xlsx`, exported from the retired Google Sheet). Old `Task ID` values (e.g. `T019`) were kept only as a join key during the import (a temporary `_import_ref` column, dropped afterward) — every imported task got a **fresh** `task_number` from the real sequence, per the "never reuse, no gaps-and-reuse risk from the old system" requirement.

**Placeholder users.** The sheet's `EMAIL_DB` tab turned out to be a real staff directory (name → company email), so almost every "Responsible" name resolved to a real, verified `@basant.info`/`@orangetree.in` address rather than a guess. For each resolved person without an existing `core.users` row, a real `auth.users` account was created (via a one-off edge function, `supabase/functions/create-placeholder-users/index.ts`, using the official Supabase Auth Admin API — not a raw SQL insert into `auth.users`, which is fragile and easy to get subtly wrong) with:
- a cryptographically random password that was never displayed, logged, or shared — the account is not usable to sign in in practice
- `email_confirm: false`
- a matching `core.users` row: `role='custom'`, `departments=[]`, `department_admin_for=[]`, `is_active=false` (belt-and-suspenders against any accidental sign-in, on top of the unknown password), **`is_placeholder=true`** (new `core.users` column, kept deliberately separate from `is_active` so the two concepts — "admin deactivated this" vs. "this was seeded as a placeholder" — don't collide when a placeholder later becomes real)

**To convert a placeholder to a real account later**: reset their password (or have them use "forgot password" against their real, already-correct email) and flip `is_active=true`. `is_placeholder` can be flipped to `false` at the same time, or left as a permanent historical marker — either is fine, nothing else reads it.

31 placeholder accounts were created this way. Full list and status: see the edge function's response (not persisted anywhere else — query `core.users where is_placeholder = true` to see the current set).

**Name resolution judgment calls** (all via `EMAIL_DB` cross-reference unless noted):
- `"Suresh Sir"` / `"Suresh Sir."` / `"Suresh sir"` (3 spelling variants, exactly the kind of case flagged in the import brief) → canonicalized to **`EMAIL_DB`'s `"Suresh Sir"` entry, which itself had a blank email** → resolved to `"Suresh S"` (`suresh@basant.info`) as the closest generic match. - `"Rajendra"` → not in `EMAIL_DB` at all.
